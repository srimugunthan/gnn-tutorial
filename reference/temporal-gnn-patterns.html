Temporal GNN Patterns

Every temporal GNN answers the same underlying question — "how does time get represented in a message-passing model?" — but the four architectures below answer it in genuinely different ways. This doc exists to keep them from blurring together, and to give you a decision framework for a real problem, especially transaction graphs, which are essentially never natural snapshots.

The single most important fork: discrete-time vs continuous-time

Before comparing architectures, separate the two ways a graph can "have time" at all:

Discrete-time (snapshot) dynamic graph
The graph is observed as a sequence of static graphs G1, G2, …, GT at fixed intervals (e.g., "the transaction graph as of the end of each day"). Time is a coarse index, not a continuous quantity. Two transactions one minute apart and one that's 23 hours apart can land in the same snapshot boundary and become indistinguishable in timing.
Continuous-time (event-stream) dynamic graph
The graph is a stream of timestamped events — edges (and sometimes nodes) that appear at exact, irregularly-spaced real-valued timestamps. Nothing is binned. A transaction at 14:32:07 and one at 14:32:09 are meaningfully close; one at 09:00:00 the next day is meaningfully far, and the model can tell the difference.
Key idea: Financial transaction graphs are continuous-time event streams by nature — transactions post whenever they post, not on a schedule the graph waits for. Forcing them into fixed snapshots (daily, hourly) is a modeling simplification that throws away exactly the fine-grained timing information — burst detection, velocity, time-since-last-transaction — that fraud and AML detection often depend on most.

Four architectures, four mechanisms

Model Time framing How time enters the model What persists across events
EvolveGCN Discrete (snapshots) The GCN's weight matrices themselves are evolved snapshot-to-snapshot by an RNN (GRU/LSTM). EvolveGCN-H treats W as the RNN's hidden state; EvolveGCN-O treats W as the RNN's output, fed forward as the next input. Weight matrices, not node states. Node embeddings are recomputed fresh from each snapshot's structure using the current (evolved) weights.
TGAT Continuous (event stream) A learned functional time encoding (grounded in Bochner's theorem, similar in spirit to Transformer positional encoding) maps a time delta into a feature vector; this is concatenated into node features and fed through self-attention over the node's temporally-ordered neighborhood. Nothing persists between queries. Every embedding is recomputed from scratch by attending over recent raw neighbor events — effectively "memory-less."
TGN Continuous (event stream) Each node owns a persistent memory vector. On every event touching a node, a message function computes an update from the event (and the two nodes' current memories); a memory updater (GRU) folds that message into the node's memory. A graph-embedding module (TGAT-style attention) then reads current memories to produce the final embedding used for prediction. A compressed per-node memory vector, updated incrementally — the model doesn't need to re-scan a node's full history at query time.
DyRep Continuous (event stream) Models two coupled processes at different time scales — topological evolution (edges/nodes appearing) and node interaction dynamics (activity between existing nodes) — as a temporal point process, with an attention-based network producing the node representations that drive both processes. Per-node latent state updated on each event, in a similar spirit to TGN's memory but framed explicitly as a point-process intensity model. Predates and partly inspired TGN's memory design.

TGN vs TGAT vs EvolveGCN, disambiguated

These three are the ones most often blurred together. The distinguishing question for each:

  • EvolveGCN — "what changes over time?" Answer: the model's parameters. The graph structure at each snapshot is processed by an otherwise-ordinary GCN, but that GCN's weight matrix is different at every snapshot, produced by an RNN that has seen all prior snapshots' weights. No per-node memory exists; everything is recomputed per snapshot.
  • TGAT — "how do I make attention time-aware?" Answer: encode the time gap between the query and each neighbor event as a learned feature, then run ordinary self-attention over the (time-encoded) temporal neighborhood. No persistent state anywhere — it's a time-aware read of raw recent history, recomputed on demand.
  • TGN — "how do I avoid re-reading a node's whole history every time?" Answer: maintain a compressed running summary (the memory vector) that's updated incrementally as events arrive, the way an RNN's hidden state summarizes a sequence without re-reading it from scratch. TGN's ablations show TGAT is actually a special case of the TGN framework without the memory module — memory is the piece TGN adds on top.
Analogy: EvolveGCN is closest to how you'd retrain a static model's weights periodically as new data batches arrive. TGAT is closest to a Transformer with time-aware positional encoding, re-run fresh on the recent context window each time. TGN is closest to an RNN with an explicit hidden state per entity — it doesn't need to re-read history because it already carries a running summary of it.

Decision framework

Situation Reach for
Data genuinely arrives as periodic full-graph exports (e.g., a nightly batch snapshot of an org chart) EvolveGCN — the snapshot framing matches the data as-is
Continuous event stream, and you need to score a new event online with minimal per-event compute TGN — incremental memory update is cheap per event; avoids rescanning history
Continuous event stream, offline/batch scoring is acceptable, and simplicity (no memory-management bugs) is valued TGAT — recompute-from-neighborhood is simpler to reason about and stateless
Need to explicitly separate "graph is growing" from "existing nodes are interacting" DyRep — its two-process framing makes that distinction explicit

Transaction graphs for AML/fraud are the canonical continuous-time, online-scoring case: new transactions arrive constantly, and a suspicious pattern often needs to be flagged before the funds clear, not at the next nightly batch. That's the practical reason TGN-style memory-based architectures show up so often in the applied fraud-detection literature — see Lesson 21.
