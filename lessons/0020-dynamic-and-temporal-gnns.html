Lesson 20

Dynamic and Temporal GNNs

Every architecture in this course so far has quietly made one more assumption on top of "one node type, one edge type": the graph doesn't change. Compute the adjacency structure once, run message passing, get an embedding. Real graphs you'd actually care about for fraud and AML aren't like that. An account isn't fixed in place with a static set of counterparties — it accumulates a stream of transactions, each one a new, timestamped edge. The graph you'd want to reason about at 3pm is not the graph you'd want to reason about at 9am. This lesson is about GNNs that treat time as a first-class input rather than an afterthought.

Two fundamentally different ways to have "time"

Before any architecture, there's a modeling fork that matters more than which specific model you pick:

  • Discrete-time (snapshot) graphs: the graph is a sequence of static graphs G1, G2, …, GT — e.g., "the transaction graph as of the end of each day." Time is a coarse index. Two events one minute apart and one 23 hours apart, if they land in the same snapshot, become indistinguishable.
  • Continuous-time (event-stream) graphs: the graph is a stream of individually timestamped events, arriving at irregular real-valued times, with no binning at all. This is what a transaction feed actually looks like.
Key idea: Financial transaction graphs are continuous-time event streams, not snapshots — money moves whenever it moves, not on a schedule the graph waits for. Forcing them into fixed snapshots throws away exactly the fine-grained timing signal (burst detection, time-since-last-transfer, velocity) that fraud and layering patterns often hinge on. This fork is developed in full in the Temporal GNN Patterns reference doc — treat this lesson as the walkthrough and that doc as the lookup table you'll come back to.

EvolveGCN: evolve the weights, not the nodes

EvolveGCN (Pareja et al., 2020) stays in the discrete-time, snapshot world, but makes an unusual choice about what "learns over time." Instead of a static GCN applied identically to every snapshot, the GCN's weight matrices themselves are evolved snapshot-to-snapshot by an RNN:

  • EvolveGCN-H treats the weight matrix W(t) as the hidden state of a GRU, updated using the current snapshot's node embeddings as input.
  • EvolveGCN-O treats W(t) as the output of an RNN, which is then fed forward as the input to produce W(t+1).

Either way, at each snapshot you get a fresh GCN — same architecture, different weights — run on that snapshot's structure. No per-node memory persists; everything about a node's representation is recomputed from the current graph and the current (evolved) weights. This matters for graphs where the node set itself changes a lot: EvolveGCN doesn't need to have seen a given node before to produce weights for it, unlike methods that maintain per-node state directly.

TGAT: time-aware attention over raw history

TGAT (Xu et al., 2020) moves to continuous time. Its central device is a functional time encoding: a learned mapping from a time delta (how long ago did this neighbor's edge form, relative to now) into a feature vector, grounded in Bochner's theorem from harmonic analysis — conceptually similar to the sinusoidal positional encodings you've seen in sequence Transformers, but learned and continuous rather than fixed and discrete. This time-encoding is concatenated onto node features, and a self-attention layer — structurally the same idea as the graph transformer lesson — attends over a node's chronologically-ordered neighborhood, weighted partly by how temporally relevant each past neighbor is.

Crucially, TGAT keeps no persistent state. Every time you want an embedding for a node, you recompute it by re-attending over its recent raw neighbor history. That's simple and stateless, but it means the "context window" of history you attend over has to be re-scanned every single query.

TGN: give every node a memory

TGN (Rossi et al., 2020) keeps TGAT's time-encoded attention idea but adds the piece TGAT is missing: a persistent memory vector per node, updated incrementally as events happen rather than recomputed from scratch each time. Three pieces work together:

  1. Message function: when an event touches a node (e.g., a transaction), compute a message from the event features and the two involved nodes' current memory.
  2. Memory updater (typically a GRU): fold that message into the node's memory, producing an updated memory vector.
  3. Graph embedding module: when a prediction is actually needed, read the current memory vectors of the node and its neighbors (using TGAT-style temporal attention) to produce the final embedding.

The memory is what makes this different from TGAT in practice: a node's entire relevant history is compressed into a fixed-size vector that updates incrementally, the same way an RNN's hidden state summarizes a sequence without re-reading it. TGN's own ablation results show TGAT is effectively a special case of the TGN framework with the memory module switched off.

Analogy: EvolveGCN is like periodically retraining a static model's weights as new batches of data arrive. TGAT is like a Transformer that re-reads its whole recent context window on every query. TGN is like an RNN with an explicit per-entity hidden state — it never needs to re-read history because it's already carrying a running summary of it forward.

DyRep, briefly

DyRep (Trivedi et al., 2019) predates TGN and shares its state-based instinct, but frames the problem as a temporal point process with two coupled dynamics operating at different time scales: topological evolution (new edges/nodes appearing) and node interaction dynamics (activity between nodes that already exist). An attention-based network produces the representations that drive both processes. It's worth knowing by name mainly because TGN's memory mechanism is a direct intellectual descendant of DyRep's per-node state updates — DyRep got there first, with a more explicit point-process framing.
