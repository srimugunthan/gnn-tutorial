Lesson 2

Graph Representations in Practice

Lesson 1 defined a graph abstractly as G = (V, E, u) with node, edge, and global feature matrices. Before we can write a single line of message-passing code, we need to answer a more mundane question: what tensors actually go into the model? This lesson is about the plumbing.

The example graph

We'll use one small graph throughout. Four nodes, four undirected edges:

The node ordering (A=0, B=1, C=2, D=3) is arbitrary — recall from Lesson 1 that a GNN must be permutation equivariant to this choice — but every representation below has to agree on some fixed ordering to stay consistent.

Representation 1: the dense adjacency matrix

The most direct encoding of connectivity is the matrix A ∈ {0,1}|V|×|V| from the glossary, with Aij = 1 if an edge connects i and j:

ABCD
A0110
B1010
C1101
D0010

Clean and intuitive — and this is exactly the object the original GCN paper (Kipf & Welling) writes its propagation rule in terms of. But it costs O(|V|2) memory regardless of how few edges exist. Real-world graphs are almost always sparse: a social network with a million users might have a few hundred edges per node, not a million. Storing 1012 mostly-zero entries to represent 108 edges is wasteful in both memory and compute.

Representation 2: the edge list (COO format)

Instead of storing the whole matrix, store only the coordinates of the nonzero entries — the pairs of connected nodes. This is called COO (coordinate) format, and it's what PyTorch Geometric calls edge_index: a tensor of shape [2, |E|], where column i gives the (source, target) pair for the i-th edge.

Key idea: Because message passing is defined edge-by-edge (gather from neighbors, aggregate, update — more on this in Lesson 4), a GNN never actually needs the full |V|×|V| matrix. It only needs to iterate over existing edges. The edge list is the natural, sparse-friendly format for that computation, which is why libraries like PyTorch Geometric and DGL use it as their default.

For our graph, treating each undirected edge as two directed entries (so information flows both ways during message passing):

edge_index = [[0, 1, 0, 2, 1, 2, 2, 3],    # source
              [1, 0, 2, 0, 2, 1, 3, 2]]    # target
# shape: [2, 8]  →  4 undirected edges stored as 8 directed entries
Analogy: This is exactly the sparse-matrix trick you've likely seen elsewhere — SciPy's coo_matrix, or how a sparse attention mask gets stored. A GNN's edge list is a sparse adjacency matrix in disguise, chosen because real graphs, like real sparse matrices, are mostly zeros.

The node feature matrix, and why row order matters

Alongside edge_index sits the node feature matrix X ∈ ℝ|V| × d from Lesson 1. Row i of X must correspond to node i as used in edge_index — there is no separate "node ID" field. If A/B/C/D have 3-dimensional features:

X = [[x_A0, x_A1, x_A2],   # row 0 → node A
     [x_B0, x_B1, x_B2],   # row 1 → node B
     [x_C0, x_C1, x_C2],   # row 2 → node C
     [x_D0, x_D1, x_D2]]   # row 3 → node D
# shape: [4, 3]

This is a common source of silent bugs when building a graph dataset by hand: if the row order in X doesn't match the index scheme in edge_index, the model trains without error but learns garbage connectivity.

Self-loops

You'll frequently see edge lists augmented with a "self-loop" for every node — an edge (i, i). This isn't part of the original graph; it's added so that when a node aggregates messages from its neighbors, it also includes its own current features in that aggregation. We'll see exactly why this matters when we derive the GCN update rule in Lesson 7 — for now, just recognize edge_index entries where source equals target as this deliberate addition, not a data error.

Batching multiple graphs

Training rarely happens on one graph. For graph-level tasks (Lesson 3), you have a whole dataset of small graphs — thousands of molecules, say — and want to process a batch of them together, the way you'd batch images. But graphs in a batch have different numbers of nodes, so you can't just stack them into a new tensor dimension the way you stack fixed-size images.

The standard trick: concatenate all graphs in the batch into one big graph with no edges between the original graphs (a block-diagonal adjacency structure), and keep a separate batch vector that records which original graph each node belongs to.

Key idea: Batching in a GNN doesn't add a batch dimension — it disjoint-unions the graphs into one larger sparse graph, plus an index vector. Message passing naturally respects this because it only ever looks at edge_index, and there are no edges connecting nodes from different original graphs, so no cross-contamination happens. The readout step (Lesson 12) then uses the batch vector to know which nodes to pool together.

Check your understanding

1. Which format avoids wasting memory on the many zero entries of a large, sparse graph?

  • Dense adjacency matrix
  • Sparse edge list
  • Full feature matrix
  • One-hot node vector
A dense adjacency matrix always costs O(|V|²) regardless of edge count. An edge list (COO format / edge_index) stores only the pairs that actually have an edge, which scales with |E| instead — the right choice when |E| << |V|², as in nearly all real graphs.

2. In an edge_index tensor of shape [2, |E|], what does column i represent?

  • The i-th node feature
  • The i-th edge's endpoints
  • The total node count
  • The graph's global attribute
Each column is one directed edge, given as a (source, target) pair of node indices. Node features live in a separate matrix X, indexed by the same node IDs that appear inside edge_index.

3. When batching several graphs together for training, how are they kept from exchanging messages with each other?

  • It pads every graph identically
  • It merges all node features
  • It keeps graphs fully disconnected
  • It averages every edge weight
Batching concatenates the graphs into one larger graph with no edges added between them — a block-diagonal structure. Since message passing only follows existing edges, nodes from different original graphs simply never appear as each other's neighbors.
