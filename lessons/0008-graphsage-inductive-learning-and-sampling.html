Lesson 8

GraphSAGE: Inductive Learning and Sampling

Lesson 7 ended on a limitation: GCN's propagation rule bakes the specific graph's normalized adjacency matrix into the model, so it's trained and evaluated on one fixed graph. GraphSAGE (SAmple and aggreGatE), from Hamilton, Ying & Leskovec (2017), was built explicitly to remove that constraint — and to make message passing tractable on graphs with millions of nodes, where even loading the full adjacency matrix into memory is a problem.

The limitation it solves: fixed-graph, full-batch training doesn't scale or generalize

Two separate problems compound in the original GCN formulation:

  • Scalability. Full-batch GCN computes a forward pass over the entire graph at once. For a graph with a billion edges, that's a lot of memory and compute per gradient step, and it only gets worse as you stack more layers — the receptive field of Lesson 5 grows to cover most of the graph.
  • Generalization to new nodes. Because GCN's aggregation weights are derived from the fixed D̃ and Ã of one graph, there's no defined way to compute an embedding for a node that arrives after training without recomputing over the whole graph again.

GraphSAGE addresses both with the same idea: stop treating the aggregation as an operation over the whole graph, and instead treat it as a function — learned once, applied locally to any node's neighborhood, on demand.

The core mechanism: sample, then aggregate

At each layer k, instead of gathering messages from all of a node's neighbors, GraphSAGE draws a fixed-size uniform sample Sk of neighbors (e.g. sample 10, even if the node has 500). The forward pass, for a node v at depth K, is:

GraphSAGE forward propagation (per node v, layer k = 1..K):
h0v = xv
hkN(v) = AGGREGATEk( { hk−1u : u ∈ sample(N(v)) } )
hkv = σ( Wk · CONCAT( hk−1v, hkN(v) ) )
hkv = hkv / ‖hkv‖2 (L2-normalize)

Two details worth flagging against the message-passing template from Lesson 4:

  • Concatenation, not fixed weighted sum. GCN mixes the self-term into the same weighted average as neighbors (via the self-loop). GraphSAGE instead concatenates the node's previous representation with the aggregated neighbor representation, then applies a learned W — giving the update more freedom to weigh "self" against "neighbors" separately, closer to a residual/skip connection.
  • Sampling makes cost independent of degree. Since Sk has a fixed size, the compute and memory cost of one node's forward pass is bounded by K and the sample sizes, not by the graph's actual degree distribution — crucial for graphs with high-degree hub nodes.

Three aggregator choices

AGGREGATEk must still be permutation-invariant (Lesson 4) since a sampled neighbor set has no inherent order. The paper evaluates three options:

  • Mean aggregator: elementwise mean of the sampled neighbor vectors — the simplest option, structurally close to GCN's rule but without degree-based weighting.
  • LSTM aggregator: feed the neighbor vectors through an LSTM for more expressive power. But an LSTM is not inherently permutation-invariant — the paper's workaround is to feed neighbors in a random order each time, adapting a sequence model to an unordered set.
  • Pooling aggregator: transform every neighbor independently through a small MLP, then take an elementwise max: aggregatepool = max({ σ(Wpool hu + b) : u ∈ N(v) }). This is a direct ancestor of the max-based expressiveness argument you'll meet again in Lesson 10.

What's new: learning a function, not a lookup table

This is the conceptual heart of the paper. Earlier node-embedding methods (and GCN, in effect) learn something closer to a table of per-node vectors, fit to one specific graph. GraphSAGE instead learns the aggregator functions and weight matrices Wk — objects that don't reference any particular node's identity or the graph's specific size. Once learned, that same function can be applied to a node's neighborhood regardless of whether that node existed during training, as long as it has features and edges to sample from.

Analogy: GCN is like memorizing a lookup table of answers for the students in one specific classroom. GraphSAGE is like learning a general study method — a new student who walks in later (a new node, with features and neighbors) can still apply the same method to produce a sensible answer, without the table being recomputed.

Inductive by construction

This is why GraphSAGE is the canonical inductive GNN: it generalizes to nodes, and even entire graphs, unseen at training time, as long as they come with node features. That's a strict requirement, though — GraphSAGE needs meaningful node features to work from (e.g. profile attributes, transaction amounts). A method relying purely on learned per-node identity embeddings, with no features at all, has nothing to compute for a brand-new node.

Key idea: Transductive vs. inductive is really a question of what the model has learned to depend on. GCN's learned parameters are entangled with one fixed graph's structure. GraphSAGE's learned parameters — the aggregator and Wk matrices — are graph-agnostic functions applied locally. This is exactly the property you'd want for a fraud graph where new accounts and transactions appear every hour and you can't afford to retrain (or reprocess the entire graph) before scoring them.

Training without labels: the unsupervised objective

GraphSAGE can be trained with ordinary supervised loss (e.g. cross-entropy on node labels) exactly like GCN. But the paper also proposes an unsupervised, graph-structure-based loss for settings without labels, based on the same intuition as word2vec-style embeddings: nodes that co-occur on short random walks should end up with similar embeddings, and randomly sampled distant nodes should not:

J(z_u) = −log(σ(z_u·z_v)) − Q·E[log(σ(−z_u·z_vn))]
# v: a node near u on a random walk
# vn: a "negative" node sampled roughly at random

This will resurface in Lesson 14 when we look at node embedding methods that predate GNNs entirely.

At each layer, GraphSAGE draws a fixed-size uniform sample of a node's neighbors rather than aggregating over all of them, so per-node cost stays bounded regardless of the node's actual degree.

3. Applying an LSTM aggregator to a node's neighbors requires which extra step to fit the permutation-invariance requirement from Lesson 4?

  • Randomly permuting neighbors before feeding the LSTM
  • Sorting neighbors by degree before the LSTM
  • Averaging neighbors together before the LSTM runs
  • Removing neighbors randomly before the LSTM runs
An LSTM processes its input as an ordered sequence, so it isn't naturally permutation-invariant. The paper's workaround is to feed the sampled neighbors in a random order each time, trading a clean theoretical guarantee for the LSTM's extra expressive power.
