Lesson 18

Heterogeneous Graphs

Every architecture so far — GCN, GraphSAGE, GAT, GIN, graph transformers — has quietly assumed one node type and one edge type. A social network's "friend" edges, a molecule's bonds: one relation, one meaning, one shared weight matrix. Most real graphs aren't like that. A citation graph has papers, authors, and venues as node types, connected by cites, writes, and published_in edges. A financial graph has accounts, merchants, and devices linked by transacts, owns, and logs_in_from edges. These are heterogeneous graphs, and treating every edge the same way throws away exactly the information that makes them useful.

Why one weight matrix isn't enough

Recall the message-passing update from earlier lessons: a node aggregates transformed messages from its neighbors, typically via hi' = σ(∑j∈N(i) W hj), with a single learned W shared across every edge. Now consider the citation graph:

An author "writing" a paper and a paper "citing" another paper are not the same kind of relationship, even though both are just edges in the adjacency structure. Squeezing them through the same W forces the model to learn one transformation that has to work for two semantically unrelated operations. The fix seems obvious once stated: give each relation type its own transformation.

Key idea: A heterogeneous graph has a typed schema — a set of node types and a set of relation (edge) types, each of which may deserve its own weight matrix. This is a strict generalization of everything so far: a graph with one node type and one edge type is just the homogeneous special case.

R-GCN: relation-specific weight matrices

R-GCN (Relational GCN, Schlichtkrull et al. 2018) is the direct extension of GCN-style message passing to multiple relations. Instead of one shared W, every relation r gets its own Wr, and a node's update sums contributions per relation:

h_i' = σ( ∑_{r ∈ R} ∑_{j ∈ N_r(i)} (1/c_i,r) W_r h_j  +  W_0 h_i )

Nr(i) is node i's neighborhood under relation r specifically, ci,r is a normalization constant (analogous to the degree normalization from the GCN lesson, but computed per relation), and W0 is a self-connection term carrying the node's own features forward — the relational analogue of the self-loop.

The parameter-blowup problem

If a knowledge graph has hundreds of relation types, R-GCN needs hundreds of full-sized weight matrices. That's both a huge parameter count and a rare-relation overfitting risk — a relation seen 20 times in training doesn't have enough data to learn a whole Wr from scratch. R-GCN's paper introduces two regularization schemes to solve this:

  • Basis decomposition: every Wr is written as a linear combination of a small shared set of basis matrices V1…VB, with only the per-relation coefficients arb being relation-specific: Wr = ∑b=1B arb Vb. Since B << |R|, this is effective weight-sharing across relations — structurally similar relations end up leaning on similar basis combinations.
  • Block-diagonal decomposition: each Wr is constrained to be block-diagonal, so it can't mix features across blocks. This is a sparsity constraint rather than a sharing constraint — it encodes the assumption that latent features cluster into groups that interact strongly within a group and weakly across groups.
Analogy: Basis decomposition for R-GCN is the same move as depthwise-separable convolutions or low-rank weight factorization in standard deep learning — express a large family of transformations as combinations of a small shared basis, trading a bit of expressiveness for a large reduction in free parameters.

HAN: meta-paths and two levels of attention

HAN (Heterogeneous Graph Attention Network) takes a different angle. Rather than one weight matrix per raw edge type, HAN organizes computation around meta-paths — hand-specified composite relations like Author–Paper–Author ("co-authorship," two authors connected through a shared paper) or Author–Paper–Venue–Paper–Author ("published in the same venue"). For each meta-path, HAN builds a homogeneous neighborhood and applies GAT-style attention within it, then combines across meta-paths with a second attention layer:

  • Node-level attention (intra-meta-path): for a fixed meta-path, weigh how much each meta-path neighbor matters — exactly the GAT mechanism from the architectures module, applied within one meta-path's neighborhood.
  • Semantic-level attention (inter-meta-path): weigh how much each meta-path itself matters for the task — co-authorship might matter more than shared-venue for predicting research topic, for instance.

HAN's strength is interpretability: you can inspect which meta-paths and which neighbors the model leaned on. Its weakness is the meta-paths are a modeling choice a human has to make in advance — the model can't discover a useful composite relation you didn't think to define.

HGT: attention without hand-picked meta-paths

HGT (Heterogeneous Graph Transformer) removes that manual step. Instead of pre-defined meta-paths, HGT decomposes every edge into a meta-relation triplet: ⟨source node type, edge type, target node type⟩. Query, key, and value projections for the transformer-style attention (recall the graph transformer lesson) are parameterized per triplet, so a "Paper cites Paper" edge and an "Author writes Paper" edge each get their own attention parameterization automatically, without anyone hand-designing which composite paths matter. Stacking HGT layers lets the model discover higher-order composite relations implicitly, the way stacking any message-passing layer expands the receptive field.

Key idea: R-GCN, HAN, and HGT all answer the same question — "how do relation-specific transformations get parameterized without the parameter count exploding?" — with three different design choices: R-GCN shares parameters via a basis of matrices, HAN shares parameters by making a human pre-specify which composite relations (meta-paths) matter, and HGT shares parameters by attention over meta-relation triplets, learning composite structure automatically.
Model Relation handling Needs hand-picked meta-paths?
R-GCN Per-relation weight matrix (basis / block-diagonal shared) No — operates on raw edge types
HAN GAT-style attention within each meta-path, then across meta-paths Yes — a human defines the meta-paths
HGT Transformer attention parameterized per ⟨type, edge, type⟩ triplet No — composite relations emerge from stacked layers

Check your understanding

1. In R-GCN, why does each relation type need its own weight matrix Wr?

  • Because different relations transform neighbor features differently
  • Because every relation needs a unique bias
  • Because shared weights increase total training time
  • Because each node type needs more features
A single shared matrix forces semantically unrelated relations (e.g., "cites" and "writes") to be squeezed through the same transformation. Relation-specific Wr lets the model learn that these relations mean structurally different things.

2. What problem does R-GCN's basis decomposition address?

  • Too many parameters across many relations
  • Too few labeled training graph examples
  • Too slow message passing computation speed
  • Too little attention across graph layers
With hundreds of relation types, storing a full Wr per relation is both expensive and prone to overfitting on rare relations. Basis decomposition writes every Wr as a combination of a small shared set of basis matrices, cutting the free parameter count sharply.

3. What is a key practical advantage of HGT over HAN?

  • It does not require hand-designed meta-paths chosen manually
  • It does not require any labeled node features
  • It does not use self-attention over neighborhoods ever
  • It does not scale to large graphs well
HAN needs a human to pre-specify which meta-paths (e.g., Author–Paper–Author) are worth attending over. HGT instead parameterizes attention per ⟨source type, edge type, target type⟩ triplet, so composite relational patterns emerge from stacking layers rather than manual specification.
