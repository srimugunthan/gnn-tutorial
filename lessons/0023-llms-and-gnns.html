LLMs + GNNs

This is a fast-moving area with no single foundational paper the way GCN or GAT have one — what follows is a synthesis across several distinct research threads, current as of writing, rather than one canonical result. Treat this lesson as a map of vocabulary and framings for reading further, not a settled textbook chapter.

The pairing makes sense once you name the asymmetry: LLMs are extremely good at open-ended reasoning over text but have no native notion of graph structure; GNNs are good at structure but only consume whatever features you hand them. Most current work combines them along one of a few recurring patterns.

Pattern 1: serialize the graph as text, let the LLM reason directly

The simplest combination skips GNNs entirely: turn the graph into a text prompt (a node list, an edge list, or some structured description) and ask an LLM to answer questions about it — "is there a path from A to D?", "what's node X's degree?" — using its general reasoning ability.

Google Research's "Talk like a Graph" (Fatemi, Halcrow & Perozzi, ICLR 2024) studied this directly and found that how you encode the graph as text matters enormously: switching encoding schemes swung LLM accuracy on graph reasoning tasks by anywhere from 4.8 to 61.8 percentage points on the same underlying task, and performance degraded further as graphs grew larger or tasks required deeper multi-hop structural reasoning.

Key idea: An LLM reasoning over a serialized graph has no architectural permutation invariance or message-passing inductive bias — recall from Lesson 1 that this was the whole reason GNNs exist. It's approximating structural reasoning through general-purpose text understanding, which works surprisingly well on small graphs and simple queries but is not a substitute for a GNN on tasks that need reliable multi-hop structure.

Pattern 2: LLMs feed better features into a GNN

A large share of real graphs are text-attributed: citation networks where nodes are papers with abstracts, product graphs where nodes are listings with descriptions, social graphs where nodes have bios. Traditionally these get embedded with something like TF-IDF or a small pretrained encoder to become the node feature matrix X from Lesson 2. A recent line of work instead uses an LLM to generate or enrich that text first — for instance, prompting an LLM to produce an explanation or expanded description for a node before embedding it — and only then hands the resulting features to an ordinary GNN for message passing.

A recent survey (Li et al., "A Survey of Graph Meets Large Language Model," IJCAI 2024) organizes this and related work into a three-way taxonomy worth knowing as vocabulary:

  • LLM as Enhancer — the LLM improves node/edge features or representations that a GNN then consumes (the pattern just described).
  • LLM as Predictor — the LLM itself makes the final prediction, given some serialization or summary of the graph (Pattern 1, pushed further).
  • GNN–LLM Alignment — the two are trained jointly, with a shared or aligned representation space so structural and textual signals reinforce each other rather than one simply feeding the other.

Pattern 3: graphs as retrieval structure for grounded generation (GraphRAG)

Standard retrieval-augmented generation (RAG) retrieves text chunks by embedding similarity. GraphRAG (Microsoft Research) instead builds a knowledge graph from the source corpus first — extracting entities and relationships, then clustering the graph into communities and generating a summary for each community — and uses that graph structure to drive retrieval: local queries traverse nearby entities and relationships, while broad "what are the themes in this corpus" queries pull from the higher-level community summaries. This targets a known weakness of plain embedding-similarity RAG: answering questions that require connecting information scattered across many documents, which a flat similarity search tends to miss.

Analogy: Plain RAG is like retrieving individual index cards that mention your query terms. GraphRAG is like retrieving index cards plus the folder structure connecting them, so the model can follow "these three entities co-occur across five documents" the way a GNN follows edges — except here the "graph" was extracted and summarized by an LLM in the first place, and the traversal is done for retrieval rather than for a differentiable forward pass.

What this doesn't replace

None of these patterns make Lessons 4–21 obsolete. Message passing is still the tool of choice when you need reliable, differentiable, permutation-equivariant structural computation over a graph you can actually put in a tensor — a transaction network for AML detection, a molecule, a citation graph you're training end-to-end. LLM integration is most useful at the edges: producing richer input features, answering open-ended questions about a graph in natural language, or grounding generation in a corpus's structure. The two are complementary tools, not competitors, and knowing when a plain GNN is the right, cheaper, more reliable answer is itself part of the literacy this module is trying to give you.
