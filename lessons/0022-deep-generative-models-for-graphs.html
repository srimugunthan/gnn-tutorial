Deep Generative Models for Graphs

Every lesson so far has asked a GNN to consume a graph and produce a prediction. This lesson flips the question: can a model produce a graph? Given a dataset of molecules, can we train something that generates new, plausible molecules? This is a genuinely different problem from message passing, and it's worth seeing why — briefly, since this module is optional broader literacy rather than core material.

Why graph generation is harder than image or text generation

A VAE for images outputs a fixed-size pixel grid; an autoregressive language model outputs one token at a time in a fixed left-to-right order. Graphs have neither property:

  • No canonical ordering. The same graph can be written down as |V|! different adjacency matrices, one per node permutation (recall permutation invariance from Lesson 1). A generative model that scores a specific matrix has to somehow not penalize a correct graph just because it came out in a different node order.
  • Discrete, structured output. Nodes and edges are discrete objects with hard constraints (an edge either exists or doesn't), unlike a continuous pixel intensity.

Two influential approaches handle this permutation problem in opposite ways: GraphVAE generates the whole graph at once and pays a matching cost after the fact; GraphRNN generates the graph piece by piece and avoids most of the matching cost by imposing an ordering during training.

GraphVAE: generate all at once, then match

GraphVAE (Simonovsky & Komodakis, 2018) follows the standard VAE recipe you already know: an encoder maps a graph to a latent vector, a decoder maps the latent vector back to a graph, and the model is trained to reconstruct its inputs through that bottleneck. The twist is entirely in what the decoder outputs and how reconstruction error is measured.

The decoder outputs a probabilistic, fully-connected graph of a fixed maximum size in one shot: an existence probability for every possible node, a predicted class for every node, and an existence probability plus edge type for every possible node pair — essentially a soft adjacency matrix and a soft feature matrix, produced directly by an MLP, with no message passing involved in decoding.

Key idea: Because the decoder has no idea which of the |V|! orderings of the target graph to aim for, GraphVAE can't just compare its output matrix to the target matrix entry-by-entry. It first solves an approximate graph-matching problem — searching for the permutation of the output graph's nodes that best aligns it to the target graph — and only then computes reconstruction loss against that best-aligned version.

That matching step is expensive: the graph-matching subroutine GraphVAE uses is an approximate relaxation, but still costs on the order of O(n4) for an n-node graph, and the O(n2) all-pairs output itself doesn't scale. In practice, GraphVAE is demonstrated on small graphs — tens of nodes, not thousands. It's an elegant proof of concept for how to handle permutation invariance in a generative loss, more than a production-scale generator.

GraphRNN: generate one piece at a time

GraphRNN (You, Ying, Ren, Hamilton & Leskovec, 2018) sidesteps the all-pairs output entirely by treating graph generation as sequence generation: add one node, decide its edges to existing nodes, add the next node, repeat, until a stop token is emitted.

Two RNNs work together: a graph-level RNN tracks the state of the graph built so far and initializes the state for each new node; a edge-level RNN then steps through the existing nodes and predicts, one Bernoulli (edge / no-edge) decision at a time, whether the new node connects to each of them. Training uses teacher forcing against real graphs with a binary cross-entropy loss, and generation at inference time samples from those Bernoulli outputs until an end-of-sequence signal is produced.

Key idea: The remaining problem is that a graph still has no single canonical node order to train the RNN on. GraphRNN's fix is to always linearize training graphs with a breadth-first search (BFS) ordering. This collapses the astronomically many equivalent orderings down to a much smaller set of BFS-consistent ones, and — because BFS visits nodes in shells — it also guarantees a new node can only connect to a bounded window of recent nodes, not the entire graph seen so far. That's what keeps each edge-level decision cheap and lets GraphRNN scale to graphs far larger than GraphVAE can handle.

GraphVAE vs. GraphRNN, side by side

GraphVAE GraphRNN
Generation style One-shot (whole adjacency matrix) Sequential (autoregressive, node by node)
Handles permutation via Graph matching at loss time Fixed BFS ordering during training
Practical scale Small graphs (tens of nodes) Much larger graphs

Both papers predate the current wave of diffusion- and flow-based graph generators, which is where most active generative-graph research has since moved — but GraphVAE and GraphRNN are still the cleanest illustration of the core problem: any graph generator has to decide how it will cope with the fact that a graph has no canonical ordering, and every later method inherits that same choice in one form or another.

Check your understanding

1. Why does GraphVAE need a graph-matching step before computing its reconstruction loss?

  • To reduce total parameter count
  • To align arbitrary node orderings
  • To increase generated graph diversity
  • To speed up decoder training
The decoder's output matrix and the target graph's matrix may represent the same graph under two different node orderings. Graph matching searches for the permutation that best aligns them so the reconstruction loss compares like with like, rather than penalizing a correct graph for an arbitrary relabeling.

2. GraphRNN orders nodes via breadth-first search before training. What does this primarily achieve?

  • It caps the number of prior nodes considered
  • It removes the need for an edge-level RNN
  • It converts the graph into a dense matrix
  • It guarantees every newly generated graph is connected
BFS ordering collapses the many equivalent node orderings into a smaller, consistent set, and because BFS visits nodes in shells, a new node's edge decisions only need to look back at a bounded recent window rather than every node generated so far.

3. A researcher needs to generate graphs with thousands of nodes and wants training to stay tractable. Which approach fits better, and why?

  • GraphRNN, since generation and loss scale near-linearly
  • GraphVAE, since matching cost stays constant always
  • GraphRNN, since it avoids using neural networks
  • GraphVAE, since dense matrices compress large graphs
GraphVAE's O(n²) all-pairs output and roughly O(n⁴) matching cost make it impractical past small graphs. GraphRNN's sequential generation with a bounded BFS window avoids both bottlenecks, which is why it was demonstrated on graphs an order of magnitude larger.
