Lesson 4

Message Passing: How Nodes Talk to Neighbors

Lesson 3 treated "L message-passing layers" as a black box that turns raw features X into embeddings H. This lesson opens the box. Message passing is the single mechanism underneath essentially every GNN you'll meet in this course — GCN, GraphSAGE, GAT, GIN are all specific choices of the functions inside the same three-step loop. Understand this lesson well and the rest of the course is mostly "which flavor of these three functions did they pick."

The gather → aggregate → update loop

One message-passing layer updates every node's representation using its current neighbors' representations. For a node i with neighborhood N(i) (from the glossary), one layer does three things:

  1. Gather / message: for each neighbor j ∈ N(i), compute a message mj→i = MSG(hi, hj, eij) — a function of the receiving node's own state, the sending neighbor's state, and (optionally) the edge feature between them.
  2. Aggregate: combine all incoming messages into one fixed-size vector: ai = AGG({mj→i : j ∈ N(i)}).
  3. Update: combine the aggregated message with the node's own previous state to produce its new state: hi' = UPD(hi, ai).

Every node in the graph runs this same three-step recipe, in parallel, using the same learned MSG, AGG, and UPD functions (weight-sharing, just like a CNN kernel reused at every pixel). Stack L of these layers back to back and you get exactly the "L message-passing layers" box from Lesson 3.

Key idea: A message-passing layer is a local, weight-shared computation: it only ever looks at a node, its direct neighbors, and the edges between them. Nothing in the layer definition requires knowing the whole graph at once — which is exactly why this scales to graphs with billions of nodes, and why edge_index (Lesson 2) is all a layer ever needs to read.

Worked example: updating node C

Let's trace one layer by hand on the four-node graph from Lesson 2 (A–B, A–C, B–C, C–D). Node C has three neighbors: A, B, and D.

# gather: one message per neighbor of C
m_A = MSG(h_C, h_A)
m_B = MSG(h_C, h_B)
m_D = MSG(h_C, h_D)

# aggregate: combine the (unordered) set {m_A, m_B, m_D}
a_C = AGG({m_A, m_B, m_D})     # e.g. sum, mean, or max

# update: fold the aggregate into C's own previous state
h_C' = UPD(h_C, a_C)

Meanwhile A, B, and D are running the exact same recipe over their own neighborhoods, at the same time. After one layer, every node's embedding has absorbed information from its immediate (1-hop) neighbors — what happens when you stack more than one layer is Lesson 5.

Why aggregation must be permutation-invariant

Notice that step 2 wrote AGG over a set {mA, mB, mD}, not a list. That's deliberate. A node's neighborhood N(i) has no canonical order — "A, B, D" and "D, B, A" describe the exact same neighbor set. The only thing that distinguishes A, B, and D from each other is their own features, carried inside each message; the order we happen to iterate over them while writing code is an implementation detail, not part of the graph.

Recall Lesson 1's permutation equivariance requirement: relabeling the nodes of a graph must not change what the GNN computes, only how the output is indexed. If AGG's result depended on the order its inputs were listed, then two people drawing the identical graph with a different node-labeling convention would get a different embedding for the same node — a GNN that isn't equivariant to a completely arbitrary choice (how you happened to number the nodes) is not usable as a general graph model.

Key idea: AGG must satisfy AGG({mA, mB, mD}) = AGG({mB, mD, mA}) = … for every permutation of the same set. Functions that reduce a set to a fixed-size vector this way — sum, mean, max — are called permutation-invariant aggregators. This single constraint is what makes message passing well-defined on graphs at all.

Choosing an aggregator: sum vs. mean vs. max

Sum, mean, and max are all valid (permutation-invariant), but they preserve different information:

Aggregator Keeps Loses Typical use
Sum Neighbor count (degree) information Scale grows unbounded with degree GIN (Lesson 10) — maximizes expressiveness
Mean A degree-normalized average signal How many neighbors contributed GCN (Lesson 7), GraphSAGE-mean
Max The single most salient neighbor signal Everyone else's contribution entirely GraphSAGE-pool
Analogy: This is the same trade-off as choosing sum-pooling vs. average-pooling vs. max-pooling in a CNN. Sum keeps a signal proportional to "how much stuff is here," mean normalizes that away, and max keeps only the strongest activation. The graph setting is more consequential, though: unlike a CNN's fixed 3×3 window, a node's neighborhood size (its degree) varies wildly across the graph, so the choice of aggregator interacts directly with degree variance.

A quick reference card capturing this whole framework in clean notation and pseudocode lives at reference/message-passing-cheatsheet.html — worth bookmarking, since GCN, GraphSAGE, GAT, and GIN are all just different (MSG, AGG, UPD) triples plugged into this same loop.

Check your understanding

1. Node C has neighbors A, B, and D. If you swap the order in which their messages are listed before aggregating, what should happen to C's updated embedding?

  • The result stays unchanged
  • The result becomes random
  • The result flips sign
  • The result loses information
Sum, mean, and max are permutation-invariant: reordering the same set of neighbor messages doesn't change the aggregated output. This is required so the computation doesn't secretly depend on an arbitrary node-listing order.

2. Which of the following aggregation functions is not permutation-invariant over a neighbor set?

  • Concatenation in listed order
  • Element-wise sum of messages
  • Element-wise mean of messages
  • Element-wise max of messages
Concatenating messages in whatever order you happened to iterate over them produces a different vector for a different ordering of the same neighbor set — it's order-dependent, not invariant. Sum, mean, and max all give the same result regardless of order.

3. A GCN-style mean aggregator divides the summed neighbor messages by degree. What does this primarily correct for?

  • Nodes with very different degrees
  • Nodes with identical feature vectors
  • Edges with missing edge features
  • Layers with too few parameters
Mean aggregation normalizes by neighbor count, so a high-degree node doesn't simply dominate by summing over more terms. Without this normalization, nodes with widely varying degree would produce aggregate messages on very different scales.
