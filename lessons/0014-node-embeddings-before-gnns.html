Lesson 14

Node Embeddings Before GNNs

Lessons 4–13 built node embeddings the message-passing way: gather, aggregate, update, stack layers, pool, train. But that isn't how the field got its first working node embeddings. From roughly 2014 to 2016 — before Kipf & Welling's GCN paper (2017) made message passing the default — the dominant approach never looked at a neighbor's features at all. This lesson covers that predecessor family: DeepWalk, node2vec, and LINE.

The shallow embedding recipe

Compare two ways of assigning node v a vector:

  • GNN encoder (Lesson 4 onward): zv = f(features of v and its neighbors; shared weights) — a function, applied to local structure and features.
  • Shallow embedding: zv = Z[v] — a single row of a directly-learned lookup table Z ∈ ℝ|V| × d, indexed by node ID. No features, no neighbor aggregation, no shared function — just one free vector per node, optimized directly.

The training objective is borrowed wholesale from NLP: skip-gram, the same idea behind word2vec (Mikolov et al., 2013). Word2vec treats "words that co-occur in a sentence window" as a training signal — nearby words should have similar embeddings. Shallow graph embeddings treat "nodes that co-occur in some generated sequence" the same way. The only real design question separating DeepWalk, node2vec, and LINE is: what counts as a sequence, and what counts as "nearby"?

DeepWalk: random walks as sentences

DeepWalk (Perozzi, Al-Rfou & Skiena, arXiv:1403.6652, KDD 2014) generates many random walks from every node: starting at v, repeatedly hop to a uniformly-random neighbor for some fixed number of steps. Each walk is a sequence of node IDs — treat it exactly like a sentence of words, and run skip-gram (with negative sampling) over it: slide a context window along the walk, and train Z so that a center node's embedding predicts the nodes that appear in its window.

Nodes that co-occur often across many such walks — because they're densely interconnected or otherwise structurally close — end up with similar embeddings. That's the whole mechanism: no features, no explicit aggregation function, just "predict my random-walk neighbors."

node2vec: biasing the walk

node2vec (Grover & Leskovec, arXiv:1607.00653, KDD 2016) keeps DeepWalk's skip-gram-over-walks skeleton but generalizes the walk itself from uniform to a 2nd-order biased random walk, controlled by two hyperparameters: return parameter p (how likely the walk is to immediately backtrack to the node it just came from) and in-out parameter q (how likely it is to venture further away vs. stay local). Formally, having just moved from t to the current node v, the unnormalized weight for stepping to a candidate x is scaled by 1/p if x = t (returning), 1 if x is also a neighbor of t (staying local), and 1/q if x is farther from t than v is (exploring outward).

Key idea: Low q biases the walk toward DFS-like exploration, producing embeddings that capture homophily — nodes in the same community end up close in embedding space. High q biases toward BFS-like exploration, capturing structural equivalence — nodes that play the same structural role (e.g. "hub" or "bridge") end up close even if they sit in entirely different parts of the graph. p and q only change the sampling strategy; the embedding table and skip-gram loss underneath are otherwise identical to DeepWalk.

LINE: no walks at all

LINE (Tang et al., arXiv:1503.03578, WWW 2015) drops random walks entirely and optimizes two proximities directly: first-order proximity (nodes joined by an edge should have similar embeddings — a direct pairwise signal) and second-order proximity (nodes with similar neighborhoods, even without a direct edge, should have similar embeddings — the "shared context" idea from skip-gram, computed from shared neighbors instead of walk co-occurrence). Each proximity is trained as its own embedding set, then the two are concatenated. LINE's motivation was explicit: scale to production social networks with hundreds of millions of edges, where generating and storing large numbers of random walks is itself a cost worth avoiding.

Why GNNs superseded shallow embeddings for most uses

Three structural limitations, all stemming from the same root cause — Z is a table indexed by node identity, not a function of anything:

  1. No node features used. DeepWalk/node2vec/LINE see only graph topology and node ID; any real feature vector you have — bag-of-words on a paper, transaction statistics on an account — is simply discarded. A GNN encoder consumes those features directly at every message-passing step.
  2. Fixed to the training graph — no inductive generalization. Z's rows correspond one-to-one to the node IDs present when training ran. A node that shows up afterward has no row and no way to get one short of rerunning the whole skip-gram training procedure. GraphSAGE, GAT, and GIN instead learn a function of local neighborhood features that applies to any node, seen or not, at inference time (Lesson 8's inductive framing). This is precisely the everyday reality of a fraud graph: new accounts and transactions appear continuously, so a detection pipeline that needs a full embedding-table retrain before it can score a new account is a non-starter operationally.
  3. No parameter sharing across the graph. Z has O(|V| × d) parameters — growing linearly with the graph — and each node's vector is optimized almost independently. A GNN's weight matrices are shared across every node and scale with feature dimension rather than node count, which is both a smaller model and, through that shared function, an implicit way for nodes to borrow statistical strength from each other.

Where shallow embeddings still make sense

None of this makes DeepWalk/node2vec/LINE obsolete everywhere:

  • Featureless, purely structural graphs — where topology genuinely is all you have, so a GNN's feature-consuming machinery has nothing extra to exploit.
  • Fixed, closed-world, transductive graphs — the node set is known upfront and won't grow, so the inductive-generalization limitation never bites.
  • Cheap baselines and fast prototyping — skip-gram training is lightweight compared to backpropagating through variable-depth neighborhood aggregation, and it's often the fastest way to get a first embedding to sanity-check against.
  • Coarse structural-similarity tasks — visualization, quick clustering — where a discriminative signal tied to rich features isn't the point.
Key idea: Shallow embeddings and GNN encoders aren't mutually exclusive. It's common to see pretrained DeepWalk or node2vec vectors used to initialize a GNN's input features, or included as one input feature among several — the historical predecessor becomes a component of the modern pipeline rather than a competitor to it.

Check your understanding

1. What is the main input to a DeepWalk or node2vec embedding, unlike a GNN?

  • Only the node's identity
  • Only the node's features
  • Only the node's degree
  • Only the node's neighbors
Shallow embeddings look up a row of a table indexed purely by node ID. They never consume node features, degree, or neighbor information directly — any structural signal they capture comes indirectly, through which nodes co-occur in random walks.

2. In node2vec, what do the return parameter p and in-out parameter q jointly control?

  • How biased the random walk is
  • How large the embedding table is
  • How many negative samples are used
  • How many GNN layers are stacked
p and q bias the 2nd-order random walk toward backtracking, staying local, or exploring outward — interpolating between DFS-like walks (homophily) and BFS-like walks (structural equivalence). They don't change the table size, the negative-sampling count, or anything about GNN layers — node2vec has no message-passing layers at all.

3. A fraud-detection graph gains thousands of new accounts every day. Why is this a problem for a DeepWalk-style shallow embedding?

  • New nodes have no learned embedding row
  • New nodes always get duplicate embedding rows
  • New edges always overwrite existing embedding rows
  • New features always corrupt existing embedding rows
Z is indexed by the node IDs seen during training; a node that didn't exist then has no row in the table and can't get one without rerunning training. An inductive GNN encoder, by contrast, computes an embedding as a function of local neighborhood features that works on nodes it has never seen.
